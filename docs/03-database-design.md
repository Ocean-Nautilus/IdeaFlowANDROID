# Проектирование базы данных

СУБД: **SQLite** через библиотеку **Room**.
Файл базы: `ideas.db`, текущая версия схемы — 1.

## Состав таблиц

ТЗ требует минимум 3 основные таблицы и 1 связующую. В проекте ровно столько.

| Таблица | Вид | Назначение |
|---|---|---|
| `categories` | основная | Категории идей: «Учёба», «Работа», «Личное» |
| `ideas` | основная | Сами идеи — главная сущность приложения |
| `tags` | основная | Справочник тегов |
| `idea_tag_cross_ref` | связующая | Связь идей и тегов многие-ко-многим |

## Схема

```
categories                       ideas
┌────────────────────┐          ┌──────────────────────────┐
│ id          PK     │◄────┐    │ id             PK        │
│ name        UNIQUE │     └────┤ categoryId     FK CASCADE│
│ colorHex           │          │ title                    │
│ createdAt          │          │ content                  │
└────────────────────┘          │ status                   │
                                │ rating                   │
                                │ isVoiceNote              │
                                │ createdAt                │
                                │ updatedAt                │
                                └───────────┬──────────────┘
                                            │
                      idea_tag_cross_ref    │
                      ┌─────────────────────▼────┐
                      │ ideaId  PK, FK CASCADE   │
                      │ tagId   PK, FK CASCADE   │
                      └──────────┬───────────────┘
                                 │
                      tags       │
                      ┌──────────▼─────────┐
                      │ id          PK     │
                      │ name        UNIQUE │
                      └────────────────────┘
```

## Связи

**Один-ко-многим: категория → идеи.**
Столбец `ideas.categoryId` объявлен внешним ключом на `categories.id`
с правилом `ON DELETE CASCADE`. Удаление категории удаляет все её идеи —
именно это требует ТЗ. По `categoryId` построен индекс, иначе выборка
идей одной категории просматривала бы всю таблицу.

**Многие-ко-многим: идеи ↔ теги.**
Реализована через таблицу `idea_tag_cross_ref`. Собственного `id` у неё нет:
первичный ключ составной, из пары `(ideaId, tagId)`. Благодаря этому один
и тот же тег невозможно повесить на идею дважды — база не даст. Оба столбца
тоже внешние ключи с `CASCADE`: удаляется идея или тег — связи уходят с ними.

В коде связь описана классом `IdeaWithDetails` через `@Relation` и `@Junction`:
Room сам делает нужные JOIN-ы и отдаёт готовый объект с категорией и списком тегов.

## Поля таблицы `ideas`

| Поле | Тип | Зачем |
|---|---|---|
| `id` | Long | Первичный ключ, генерируется базой |
| `title` | String | Заголовок, по нему идёт поиск |
| `content` | String | Текст идеи, тоже участвует в поиске |
| `categoryId` | Long | Внешний ключ на категорию |
| `status` | String | `NEW` / `IN_PROGRESS` / `DONE` / `POSTPONED`, фильтр №2 |
| `rating` | Int | Оценка 0–5, один из вариантов сортировки |
| `isVoiceNote` | Boolean | Идея надиктована голосом (изюминка, неделя 11) |
| `createdAt` | Long | Время создания в миллисекундах, сортировка по дате |
| `updatedAt` | Long | Время последнего изменения |

Статус хранится строкой, а не числом: если позже добавится новый статус,
порядок элементов перечисления перестанет иметь значение и старые записи
не «переедут» на чужой статус. За преобразование отвечает класс `Converters`.

Даты хранятся числом миллисекунд — это самый переносимый вариант,
не зависящий ни от часового пояса, ни от формата даты в системе.

## Работа в фоновом потоке

Все методы записи в DAO объявлены как `suspend`, методы чтения возвращают
`Flow`. Это означает, что обратиться к базе из главного потока нельзя
физически — компилятор не пропустит. Требование ТЗ «работа с БД в фоновом
потоке» выполняется самой конструкцией, а не дисциплиной программиста.

`Flow` даёт ещё одно: когда данные в таблице меняются, подписанный экран
получает новый список сам, без ручного обновления.
